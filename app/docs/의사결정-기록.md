# 의사결정 기록

왜 이렇게 만들었는지. **기존 구현을 바꾸기 전에 여기를 먼저 읽을 것.**
대부분은 한 번 다른 방식으로 시도했다가 문제를 만나고 옮겨온 것들이다.

---

## GPS

### 칼만 필터만으로는 부족하다 — 노이즈 게이트를 함께 쓴다

칼만 필터로 좌표를 평활화하는 것까지는 흔한 방법이다. 그런데 **가만히 서
있어도 좌표가 계속 흔들려서 분당 100m 씩 유령 거리가 쌓인다.** 계산해 보면
정확도 ±8m 환경에서 칼만 게인이 0.4 근처라, 지터 하나당 3m 씩 움직인 것으로
잡힌다.

그래서 두 단계를 더 뒀다.

1. **도플러 속도 우선** — GPS 칩이 주는 `Position.speed` 는 위치 오차의
   영향을 받지 않아 정지 판정에 훨씬 정확하다. 이게 이동을 확인해 주면
   그것만 믿는다.
2. **노이즈 게이트** — 칩 속도가 0 으로 오는 경우는 "정말 멈춤"과 "속도
   미지원"이 구분되지 않는다. 그때는 변위가 `정확도 x 0.5` (최대 4m)보다
   작으면 이동으로 세지 않는다. 측정 오차보다 작은 움직임은 실제 이동인지
   알 방법이 없다.

게이트 상한을 4m 로 둔 이유: `distanceFilter` 가 5m 라 그보다 크면 실제
보행까지 잘려 나간다.

### 일시정지는 스트림을 pause 하지 않고 끊는다

`StreamSubscription.pause()` 를 쓰면 GPS 는 계속 돌면서 이벤트만 쌓인다.
배터리도 낭비되고, 재개할 때 옛날 타임스탬프가 한꺼번에 밀려든다.
구독을 취소하고 재개할 때 다시 건다.

### 30초 넘게 끊긴 구간은 선을 잇지 않는다

일시정지든 터널에서 신호가 끊긴 거든, 지나지 않은 길을 직선으로 그으면
거리도 경로도 거짓말이 된다. 원인을 구분하지 않고 시간 간격만 본다.

### 앱이 강제 종료돼도 기록을 버리지 않는다

기록 중 통계(거리·이동시간)는 메모리에만 있다가 종료 시점에 저장된다.
앱이 죽으면 통계는 날아가고 좌표만 남는데, 그 좌표는 이미 필터를 통과한
값이라 통계를 다시 계산할 수 있다. 실제로 걸은 기록을 지우는 것보다
복원하는 편이 낫다 (`WalkRepository.recoverUnfinished`).

고도는 복원하지 않는다. 원본 고도가 노이즈 그대로라 다시 계산하면 오히려
부정확해진다.

## 코스 매칭

### Jaccard 를 버리고 포함 계수를 쓴다

처음엔 Jaccard(교집합/합집합)로 만들었다가 테스트가 실패하면서 두 가지
문제가 드러났다.

1. **짧은 코스에 지나치게 가혹하다.** 5셀짜리 코스에서 셀 하나만 어긋나도
   4/6 = 0.67 로 떨어진다. 한 블록 돌아간 것뿐인데 다른 코스로 갈라진다.
2. **코스가 클수록 자기 자신과도 안 맞는다.** 코스는 산책을 거듭할수록
   셀을 흡수해 커지는데, Jaccard 는 분모만 불어나서 오래된 코스일수록
   매칭이 깨진다.

포함 계수(교집합 ÷ 작은 쪽 집합)는 "이번 산책이 코스 위에 얼마나 올라가
있나"를 재기 때문에 코스 크기에 영향받지 않는다. 짧은 산책이 긴 코스
일부에 얹히는 문제는 **거리 허용치(±35%)로 따로 막는다.**

### 최소 4셀 이상만 코스로 묶는다

geohash 7 셀이 약 150m 라, 수백 미터짜리 산책은 한두 셀에 다 들어간다.
그런 걸 코스로 묶으면 아무 코스에나 붙는다. 실제 강아지 산책이 보통
1km 이상이라 이 기준이 과하지 않다.

(테스트를 만들 때 이걸 몰라서 156m 짜리 경로로 시험하다 실패했다.
앱 버그가 아니라 테스트 데이터가 비현실적이었던 경우다.)

## 반려견 프로필

### 처음부터 다대다

다견 가정이 드물지 않다. 나중에 바꾸면 마이그레이션이 훨씬 비싸다.

### 여러 마리면 가장 약한 아이에 맞춘다

대형견에 맞추면 함께 나간 노령 소형견이 무리하게 된다.

### 프로필을 빼도 산책 기록은 남긴다

실제로 걸었던 사실까지 사라지면 통계가 어긋난다. `is_active` 플래그로
목록에서만 감춘다. 완전 삭제는 별도 메서드로 분리해 뒀다.

### 한 마리뿐이면 선택을 묻지 않는다

매번 같은 선택을 시키는 건 방해일 뿐이다.

### 프로필 항목은 추천 엔진의 입력이다

지금은 권장 산책량 계산에만 쓰지만, 각 항목이 추천 가중치로 이어지도록
골랐다. 단두종 → 여름 시간대 하드 필터, 나이 → 경사도 가중치,
사교성 → 혼잡도 가중치. 새 항목을 추가할 때도 이 기준으로 판단할 것.

### 권장 산책량은 거리가 아니라 시간이 목표다

처음에는 거리를 목표로 잡았다. 근거를 찾으러 갔다가 **미터 단위로 말하는
수의학 가이드라인이 아예 없다**는 걸 알고 뒤집었다. 가이드라인은 시간으로
말하고, 몸집이 아니라 견종으로 나눈다.

거리를 목표로 두는 한 어떤 문헌도 인용할 수 없다. 지금 거리는 걸음 속도를
곱해 환산한 참고치일 뿐이다. **되돌리지 말 것.**

### 노령견의 산책량을 깎지 않는다

예전에는 0.6배로 줄였다. 방향이 거꾸로였다. COAST 합의 가이드라인과
AAHA 2022 에서 **통제된 규칙적 운동은 관절염의 1차 치료**다. 줄일 대상이
아니라 유지할 대상이다.

지금은 총량을 유지한 채 횟수를 늘려 나눈다. 쉬는 동안 관절이 굳기 때문에
간격을 좁히는 게 요점이다. 직관적으로는 "나이 들었으니 줄이자"가 맞아
보여서 되돌리기 쉬운 지점이라, 테스트로 못을 박아 뒀다.

### "월령 × 5분" 규칙은 버렸다

자견 기준으로 가장 널리 쓰이는 규칙이지만 **한 번도 검증된 적이 없다.**
활동적인 견종에겐 부족하고 토이 견종이나 단두종에겐 과하다.

대신 Krontveit 2012 가 실제로 보여 준 것을 쓴다 — 중요한 건 "얼마나"가
아니라 "어떻게"다. 3개월 이전 계단은 고관절 이형성증 위험을 높였고,
부드럽고 굴곡진 지면에서의 자유 운동은 오히려 낮췄다.

근거 전체는 [권장산책량-근거.md](권장산책량-근거.md).

## 테마

### 화면을 두 벌 만들지 않는다

디자인 핸드오프가 1a(포근한 안)와 1b(미니멀 안) 두 벌로 왔다. 화면을
복제하고 싶은 유혹이 있지만, 그러면 이후 모든 수정을 두 번씩 해야 한다.
기능이 바뀔 때마다 한쪽만 고치고 넘어가는 사고가 반드시 난다.

두 안은 **정보 구조와 탭 구성이 완전히 같다.** 다른 것은 색·글꼴·모서리·
구분선뿐이다. 그래서 `PetWalkTokens`(ThemeExtension)에 그 차이를 값으로
뽑아 두고 화면은 토큰만 읽는다. 새 화면을 만들 때도 이 규칙을 지킬 것 —
`if (variant == ...)` 로 갈라 쓰기 시작하면 금방 엉킨다.

### 글꼴은 번들하지 않고 받아 쓴다

두 안의 인상 차이는 대부분 글꼴에서 온다. 그래서 `google_fonts` 로 실제
글꼴을 쓰되, 앱에 넣지 않고 받아 쓴다.

한글 글꼴이라 파일이 크기 때문이다 — 다섯 벌을 합치면 **약 17MB**이고
Gowun Dodum 하나만 7MB다. 아직 두 안 중 무엇으로 갈지 정하지 않은 단계에서
치르기엔 비싼 값이다.

**한 안으로 정해지면 그때 번들할 것.** 필요한 글꼴이 두 벌로 줄어 비용이
크게 떨어지고, 망이 없는 곳에서도 디자인이 유지된다. 산책 앱이라 지하나
산 속에서 쓰이는 걸 생각하면 최종적으로는 번들이 맞다.

### 글꼴을 두 벌 모두 미리 받는다

글꼴이 첫 프레임보다 늦게 오면 대체 글꼴로 잰 크기와 실제로 그릴 크기가
어긋나 렌더링이 깨진다(`debugSize == size`). 실제로 겪었다.

쓰는 쪽만 받아서는 안 된다. **테마를 바꾸는 순간 반대편 글꼴을 처음 받게
되어 같은 문제가 다시 난다.** 그래서 시작할 때 두 벌을 모두 받는다.
실패해도 앱은 뜨고(대체 글꼴), 타임아웃도 둔다.

### 테마 전환 버튼을 산책 탭 맨 위에 둔다

설정 안쪽에 묻으면 두 안을 견줘 보기가 번거롭다. 지금은 어느 쪽이 나은지
고르는 단계라 한 번에 눌러 바로 비교할 수 있어야 한다.
**결정이 끝나면 "우리 아이" 탭의 설정 목록으로 옮길 자리다.**

## 플랫폼

### 지도는 지금 OSM 타일, 나중에 네이버/카카오

국내 지도 데이터 반출 제한 때문에 구글맵은 도보 경로 품질이 떨어진다.
국내 서비스로 나가려면 네이버 또는 카카오 SDK 로 갈아타야 한다.
교체 지점을 `widgets/route_map.dart` 하나로 묶어 뒀다.

### 웹에서는 워커 없는 sqlite 를 쓴다

`databaseFactoryFfiWeb`(워커 방식)은 SharedArrayBuffer 가 필요하고, 그러려면
서버가 COOP/COEP 헤더를 내려줘야 한다. `flutter run` 개발 서버는 그 헤더를
주지 않아서 `openDatabase` 가 조용히 null 을 반환한다.
`databaseFactoryFfiWebNoWebWorker` 로 해결했다.

### 조건부 import 는 `dart.library.io` 역조건으로

웹 판별 조건(`js_interop`, `html`)은 컴파일러와 Dart 버전에 따라 결과가
달라진다. `dart.library.io` 는 네이티브에서만 참이라 판별이 확실하다.

```dart
export 'db_platform_web.dart' if (dart.library.io) 'db_platform_io.dart';
```

## 테스트

### 두 층으로 나눴다

`testWidgets` 는 가짜 시계 위에서 도는데 sqflite 는 실제 비동기 I/O 라서,
화면 테스트 안에서 DB 를 기다리면 영원히 끝나지 않는다. 실제로 8분 타임아웃을
겪고 나서 나눴다.

- `test/` — 서비스 계층. 기기 없이 `flutter test` 로 돌아간다
- `integration_test/` — 화면까지. 기기나 에뮬레이터 필요

### 지도 타일은 테스트에서 끈다

`flutter_map` 이 타일을 계속 재시도하면서 프레임이 멈추지 않아 테스트가
끝나지 않는다. `RouteMap.tilesEnabled = false` 로 막는다.

### 시뮬레이션 좌표에 반드시 노이즈를 섞는다

오차 없는 좌표만 넣으면 필터가 하는 일이 없어서 검증이 되지 않는다.
`test/support/walk_simulator.dart` 가 ±3m 지터를 섞고, **노이즈를 뺀
참값으로 실제 경로 길이를 따로 계산해** 필터 정확도를 잰다.
